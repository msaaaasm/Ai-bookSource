### 错误分析

#### 错误1：ruleContent缺少nextContentUrl字段

**标准答案**：
```json
{
  "ruleContent": {
    "content": "#chaptercontent@html##<div id=\"content_tip\">[\\s\\S]*?</div>|本章节未完，点击下一页继续阅读|歌书网.*com##",
    "nextContentUrl": "text.下一@href"  // ✅ 有此字段
  }
}
```

**错误输出**：
```json
{
  "ruleContent": {
    "content": "#chaptercontent@html##<div id=\"content_tip\">[\\s\\S]*?</div>|本章节未完，点击下一页继续阅读##"
    // ❌ 缺少 nextContentUrl 字段
  }
}
```

**问题原因**：
1. 智能体没有检测到正文页有"下一页"按钮
2. 没有检查HTML中是否有分页元素
3. 正则表达式也不完整，缺少了 `|歌书网.*com##` 部分

**影响**：
- 无法自动跳转到下一页继续阅读
- 用户需要手动点击下一页

**修复方法**：
1. 分析正文页HTML，查找"下一页"、"下一章"、"继续阅读"等按钮
2. 如果存在这些按钮，必须添加 `nextContentUrl` 字段
3. 正则表达式必须包含所有需要清理的广告和提示文本

#### 错误2：ruleContent正则表达式不完整

**标准答案**：
```json
"content": "#chaptercontent@html##<div id=\"content_tip\">[\\s\\S]*?</div>|本章节未完，点击下一页继续阅读|歌书网.*com##"
//                                                                      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 缺少这部分
```

**错误输出**：
```json
"content": "#chaptercontent@html##<div id=\"content_tip\">[\\s\\S]*?</div>|本章节未完，点击下一页继续阅读##"
//                                                                      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 缺少网站标识清理
```

**问题原因**：
1. 智能体没有分析所有需要清理的内容
2. 遗漏了网站标识文本的清理

**影响**：
- 正文内容中可能包含"歌书网xxx.com"等网站标识
- 影响阅读体验

**修复方法**：
1. 仔细分析正文HTML，找出所有需要清理的广告和提示文本
2. 使用 `|` 分隔多个清理规则
3. 确保所有规则都以 `##` 结尾

#### 错误3：ruleToc缺少nextTocUrl字段

**标准答案**：
```json
{
  "ruleToc": {
    "chapterList": ".directoryArea p",
    "chapterName": "a@text",
    "chapterUrl": "a@href",
```

```json

  }
```

**问题原因**：
1. 智能体没有检测到目录页有分页选择器
2. 没有检查HTML中是否有 `<select>` 元素或分页链接

**影响**：
- 无法获取第二页及之后的章节
- 书源功能不完整

**修复方法**：
1. 分析目录页HTML，查找 `<select>` 下拉选择器
2. 查找"下一页"、"更多章节"等分页链接
3. 如果存在这些元素，必须添加 `nextTocUrl` 字段

## 案例二：起点图网 —— WAF 白屏、分页越界、接口 404、选择器与 Rhino 陷阱

### 一、 背景与定位

[起点图网.json](../book_sources/起点图网.json) 对应的数据站点为 **起点图**（`https://www.qidiantu.com/`）。
该站点的定位是 **起点中文网的数据分析与书单书评平台**（提供昨日新书首订榜、月度首订、盟主榜、潜力榜、大神新书、荣誉徽章、起点封推/强推/三江推荐、书单评论等），**不是**提供小说正文章节的阅读站点。
在阅读 App 中，该书源的核心价值在于**发现好书、查阅网文行业数据与书友书评**。

---

### 二、 核心错误原因深度复盘

本次排查共诊断出 **5 大典型技术错误**，覆盖了网络反爬、分页越界、接口变动、选择器规范以及底层 JavaScript 引擎（Rhino）跨语言调用的致命陷阱。

---

#### 错误 1：直连高防第三方站点导致的大面积白屏（WAF 反爬拦截）

##### 1. 现象描述
在书源发现分类中，原本配置了 40 余个“起点榜单”（包括月票榜、推荐榜、收藏榜、玄幻/都市/仙侠等分类排行、完本榜、畅销榜等），用户在阅读 App 中点击任何一个榜单进去都是**一片空白、没有任何书籍**。

##### 2. 根本原因
* 原书源在这些分类中直接配置了起点中文网官网的 URL：`https://www.qidian.com/rank/yuepiao/page{{page}}` 等。
* 起点中文网官方目前开启了**高强度腾讯云 WAF 反爬保护机制**。当使用手机客户端的简单 HTTP 请求（缺少浏览器指纹和会话 Cookie）访问时，服务器直接返回 **HTTP 202 状态码**，响应内容仅有 209 字节的 `<script src="/probe.js">` 质询探针。
* 阅读 App 无法执行探针过盾，解析到的 HTML 只有空 body，因此提取到的图书列表为 0，页面全白。

##### 3. 避坑原则
> [!WARNING]
> * **切忌在书源中随意嫁接外部未逆向破防的高防站点**。本站数据源是哪个网站，发现分类就应严格使用该网站本站的原生路由。
> * 若外部源开启了 JS Challenge、WAF 盾或 Cloudflare 质询，简易 HTTP 请求必死，必须剔除或使用专门的过盾代理/WebView 处理。

---

#### 错误 2：随机数生成算法未校准站点分页引发的 HTTP 567 崩溃

##### 1. 现象描述
在发现列表中点击“书单2”或“书单3”，有大概率或必然出现**点进去没内容**，甚至控制台报错。

##### 2. 根本原因
* 原书源在 `exploreUrl` 中为书单配置了随机获取页面的 JS 逻辑：
  * 书单2：`i1 = Math.floor(Math.random() * 17) + 4;` （随机生成 4 ~ 20 页）
  * 书单3：`i1 = Math.floor(Math.random() * 40) + 21;` （随机生成 21 ~ 60 页）
* 经实测抓包，起点图网站的书单索引页 `/booklists/` **目前只有 0 ~ 4 页（共 5 页）**！
* 当请求第 5 页及以后的地址时（如 `/booklists/5/`、`/booklists/20/`），服务器直接响应 **HTTP 567 异常状态码**；导致 `.match(/booklist\/\d+/g)` 返回 `null`，后续执行 `null[0]` 抛出 `TypeError` 异常，URL 拼接成 `undefined/0` 导致 404。

##### 3. 避坑原则
> [!IMPORTANT]
> * 书源编写动态规则（尤其是随机数、页码偏移、日期回退）时，**必须先行探查目标站点的实际数据量与有效分页范围**。
> * 动态计算必须编写**完备的空值容错和兜底保障**，例如 `(m ? (m[idx] || m[0]) : 'booklist/defaultId')`，防止上游改动导致客户端抛错闪退。

---

#### 错误 3：搜索接口变动 404 与 JSoup 类选择器带空格语法失效

##### 1. 现象描述
在搜索框中搜索任何小说（如“宿命之环”、“全职高手”），结果直接显示**搜索失败：HTTP状态码 404**，没有任何结果，自然也不会显示书籍图片。

##### 2. 根本原因
* **接口变更（404）**：原书源使用的搜索链接为 `https://www.qidiantu.com/book/`，此接口在原网站改版后已被彻底废弃并返回 404。通过分析网站前端 `search.php` 内绑定的 `booknamesearch()` 函数，实际有效接口已变更为：
  ```javascript
  window.location.href = "/bookxyy/" + value;
  ```
* **JSoup 类名解析缺陷**：原 `ruleSearch.coverUrl` 编写为：
  ```json
  "coverUrl": "class.media-left media-middle@a@img@src"
  ```
  在阅读底层的 JSoup 解析中，`class.` 后面的规则会被传入 `Element.getElementsByClass(className)`。在 JSoup 规范中，**类名参数严禁带有空格**（空格被视为复合类），传入带有空格的类名会导致定位失败或返回空集合。

##### 3. 避坑原则
> [!TIP]
> * 遇到搜索 404 或无响应，优先检查网页源代码中的 `<form action="...">` 或绑定的 `onkeydown`/`onclick` JavaScript 提交逻辑。
> * 在阅读原生规则中，尽量避免写 `class.类名A 类名B`；若需要层级定位，在单个卡片内通常直接用标签即可（如 `img@src`），或者使用标准的 CSS 选择器 `@css:.media-left img@src`。

---

#### 错误 4：封面规则硬编码列索引与结构遗漏导致图片大面积缺失

##### 1. 现象描述
* 发现里的“起点推荐”（封推、强推、三江等）所有书籍**完全没有封面**；
* 发现里的“书单”点进去后，里面列出的书籍**也全都没有封面**；
* 部分榜单在网站改版列顺序微调后，封面解析直接落空。

##### 2. 根本原因
* **推荐榜完全遗漏**：在原 `ruleExplore.coverUrl` 的庞大 `if-else` 分支中，包含了 `booklist/`、`shouding/`、`badge/`、`twelvekings` 等，但**唯独完全漏掉了 `bang/`**！匹配不到任何条件时直接返回 `undefined`，推荐榜书籍全部失去封面。
* **书单提取逻辑目标元素错误**：书单详情页中，书籍卡片是 `.well.well-sm.table-responsive`，而原规则写了：
  ```javascript
  s = java.getString('class.panel-heading.0@a.0@href');
  ```
  `.panel-heading` 是书单顶部的标题框才有的类，每本书的容器里根本没有这个元素，提取出来的 `s` 为 `""`，随后执行 `s.match(/\d+/)[0]` 直接崩掉。
* **硬编码 `td` 列位极度脆弱**：首订榜作者在 `td.7`、月度首订在 `td.3`、盟主榜在 `td.3`、十二天王在 `td.5`，原规则针对不同 URL 写了大量 `x('td.1@a.0@href')`、`x('td.2@a@href')`，极易因前端排版改动而全部失效。

##### 3. 避坑原则
* **寻找全站业务核心统一主键**：
  在起点图网站中，不论是表格 `tr`、书单卡片 `well` 还是搜索卡片 `media`，书籍链接的地址恒定为：
  $$\text{URL 模式: } \texttt{/info/\{bookId\}}$$
  而起点官方的高清封面 CDN 结构恒定为：
  $$\text{封面 CDN: } \texttt{https://qidian.qpic.cn/qdbimg/349573/\{bookId\}/180}$$

#### 错误 5：Mozilla Rhino 引擎对 Java 对象的重载匹配冲突（EvaluatorException）

##### 1. 现象描述
用户在阅读 App 中点击进入「新书潜力榜」时，弹出红色错误提示：
```text
com.script.ScriptException: org.mozilla.javascript.EvaluatorException: 
对应于 JavaScript 参数类型 (object,string) 的 Java 方法 java.lang.String.replace 的选择不明确。
建议的方法是：
  class java.lang.String replace(java.lang.CharSequence,java.lang.CharSequence)
  class java.lang.String replace(char,char) (<Unknown Source>#7) in <Unknown Source> at line number 7
```

##### 2. 根本原因
* 阅读 App 在 Android 端运行 JavaScript 规则时使用的是 **Mozilla Rhino 引擎**。
* 在规则的 `<js>` 环境中，调用 `java.getString(...)` 返回的是**原生 Java 的 `java.lang.String` 实例**，而不是 JavaScript 内置的 `String` 原型。
* 在 Java 语言中，`java.lang.String.replace` 只有两个重载方法：
  * `replace(CharSequence target, CharSequence replacement)`
  * `replace(char oldChar, char newChar)`
* 原规则写成了：
  ```javascript
  java.getString('h4@text||a@text||text').replace(/（点击查看推荐效果）/g, '').trim();
  ```
* 传入的第一个参数是 JavaScript 的 `RegExp` 对象（类型为 `object`），第二个参数是 `string`。Rhino 试图在 Java 的 `java.lang.String` 类上寻找匹配的方法，但发现既不是两个字符，也不是两个字符串序列，因此抛出“方法选择不明确”的致命异常，导致列表加载中断。

##### 3. 避坑原则
> [!CAUTION]
> 1. **优先使用阅读原生规则（免 JS 脚本）**：
>    能用原生 CSS + 正则替换的，**坚决不写 `<js>`**！原生规则由 Kotlin + JSoup 在底层直接执行，执行速度比 Rhino 快数十倍，且 100% 不会发生 Rhino 跨语言类型转换崩溃。
>    例如：
>    ```json
>    "name": "@css:a[href*=\"/info/\"]@text||h4@text##^\\[.*?\\]",
>    "author": "@css:a[href*=\"/author/\"]@text##\\(Lv\\.\\d+\\)|^Lv\\.\\d+",
>    "bookUrl": "@css:a[href*=\"/info/\"]@href##/[dm]$"
>    ```
> 2. **若必须在 JS 中对 Java 字符串做正则操作，必须先显式包装为 JS 原生 String**：
>    ```javascript
>    // ❌ 危险写法：对 Java 字符串直接调 JS 正则
>    java.getString('xxx').replace(/abc/g, '');
>
>    // ✔️ 安全写法：强制转为 JS 原生字符串后再调
>    String(java.getString('xxx') || '').replace(/abc/g, '');
>    ```

#### 错误 6：书单评论正文规则未匹配完整卡片容器与来源 footer

## 案例三：绅士漫画 —— 搜索页误判为详情页与结构适配

> 记录日期：2026-10-20
> 主题：ookUrlPattern 误判导致搜索结果被吞掉、搜索页直接进入详情页解析

## 一、现象

在绅士漫画书源中，搜索功能表现异常：

- 搜索结果只剩 1 条，或者直接没有正常列表；
- 现象类似“搜索页被识别成详情页”；
- 站点看起来能够打开，但列表和详情的判定被提前打断。

用户反馈中明确表现为：“搜索只能搜到一个，好像是阅读直接把搜索网址识别成详情页了”。

---

## 二、根因

根因不在页面结构，而在阅读的底层判定：

- `bookUrlPattern` 过宽，命中了 `/search` 这类非详情页路由；
- 阅读在搜索阶段先执行 `baseUrl.matches(bookUrlPattern)`；
- 一旦命中，底层会把当前链接当作“详情页”，并提前调用详情页解析逻辑；
- 结果是 `ruleSearch.bookList` 根本没有机会执行，最终只剩单本页面或空列表。

这类问题在项目里的通用结论也已经提到：

> `bookUrlPattern` 必须且只能匹配单本详情页，不能包含 `search`、`albums` 或其他列表页路由。

---

## 三、问题定位过程

### 1. 误判入口

检查源文件中关键字段：

- `bookSourceUrl`
- `bookUrlPattern`
- `searchUrl`
- `ruleSearch.bookList`

发现 `bookUrlPattern` 之前覆盖了搜索地址，导致搜索请求被当成书籍详情。

### 2. 验证方式

已用 Python 实际验证正则行为：

```python
import json, re
p = r'd:\Codes\项目\AiWritingLegado\book_sources\绅士漫画.json'
obj = json.load(open(p, encoding='utf-8'))[0]
pat = re.compile(obj['bookUrlPattern'])
print(bool(pat.search('https://www.wnacg.com/search/?q=abc&p=1')))
print(bool(pat.search('https://www.wnacg.com/photos-index-aid-123456.html')))
```

验证结果为：

- 搜索 URL：`False`
- 详情 URL：`True`

也就是搜索页已从详情页匹配中剔除，问题得到确认。

---

## 四、修复方案

修复思路是收紧 `bookUrlPattern`，只保留真正的详情页入口：

```json
"bookUrlPattern": "https?:\\/\\/(?:www\\.)?(?:wnacg\\w*|wn\\d+)\\.(?:com|org|ru|net|link|cfd|xyz|top|cc|me|site|online)\\/(?:photos(?:-|/)|albums(?:-|/)|comment(?:-|/))"
```

修复后，符合规则的 URL 是：

- `https://www.wnacg.com/photos-index-aid-123456.html`
- `https://www.wnacg.com/albums-index-page-1-cate-5.html`
- `https://www.wnacg.com/comment-index-aid-123456.html`

不再命中：

- `https://www.wnacg.com/search/?q=...`

---

## 五、修复后验证

再次验证匹配结果：

- `search False OK`
- `detail True OK`
- `detail2 True OK`
- `comment True OK`

这说明：

- 搜索页已不再被判定为详情页；
- 真正的书籍详情页仍然能被识别；
- 搜索与阅读链路恢复正常。

---

## 六、注意事项 / 后续遗留

### 1. `bookUrlPattern` 只能写“详情页”

不要把列表搜索地址放进去。误写会导致：

- 搜索结果被提前短路；
- 详情页解析在错误时机触发；
- `ruleSearch.bookList` 完全失效。

### 2. `searchUrl` 必须独立工作

搜索页应由：

- `searchUrl`
- `ruleSearch.bookList`
- `ruleSearch.bookUrl`

这一整条链路共同处理，而不是由详情页判定抢先接管。

### 3. 每次调整 URL 规则后，必须做正则验证

有经验表明，这类问题很容易在“看上去普通”的路径过滤中悄悄出错，因此要保留最小验证：

- 搜索 URL 不匹配
- 详情 URL 匹配
- 评论/目录 URL 也能匹配

### 4. 真机与模拟器都需确认

这类问题属于底层读取器判定问题，不能只看现象“看起来像正常”。需要确认：

- 搜索功能是否返回正常列表；
- 点击条目是否进入详情；
- 目录和正文是否正常打开。

---

## 七、可推广结论

这次问题属于“书源路由判定误差”，其可复用经验如下：

- 列表路由、详情路由、搜索路由必须分离；
- `bookUrlPattern` 不要有 `search`；
- `ruleSearch` 需要保留原始搜索列表处理逻辑；
- 修正 URL 规则后，要用最小脚本验证路由分类。

这类问题很容易让人误以为是搜索规则本身问题，实际上根因通常在最前面的 URL 类型判定。

## 八、补充：2026-10-20 WNACG 搜索/发现页结构差异复盘

### 现象

在进一步排查时，搜索页、发现页、移动端/桌面端页面的 HTML 结构并不一致，导致此前的临时修复方案又出现：

- 发现页打不开；
- 搜索页虽然请求成功，但结果仍为空；
- 同一套选择器在不同页面上的行为不一致。

### 真正原因

这次复现的核心问题不再是单一的 `bookUrlPattern`，而是：

1. `searchUrl` / `exploreUrl` / `ruleSearch` / `ruleExplore` 被混用成一套规则；
2. 搜索页与发现页并不共用同一 DOM 结构；
3. 站点不同 UA 下也可能显示不同列表结构；
4. 书源规则过度依赖 `li.gallary_item`、`div.title`、`a span` 等页面样式类名，而没有优先锁定真实结果链接。

### 真实站点观察

实际验证表明：

- 搜索页有真实结果列表；
- 第一条结果链接是 `/photos-index-aid-396136.html`；
- 分类页/发现页并不是同一套 `li.gallary_item` 列表结构；
- 桌面端和移动端 UA 也会出现不同的 DOM 生成方式。

### 结论

这类问题的根因并非“网站没内容”，而是：

- URL 规则过旧；
- 页面结构被错误抽象；
- 搜索页、发现页、详情页分支混在同一套规则中；
- 选择器假设了一个统一 DOM，而真实站点并没有。

### 最终可复用的经验

在 WNACG 这类站点上，最稳妥的策略是：

- 先抓真实页面 HTML，再确认结果项的真实节点；
- 先锁定 `a[href*='photos-index-aid-']` 这类真实结果链接；
- 再分别处理搜索页与发现页的规则；
- 不要把多个页面结构强行塞进同一份规则；
- 每次修复后必须进行 “搜索页 / 发现页 / 详情页” 三路验证。

### 一句话复盘

> 不要把“看起来相似”的页面打包成同一套规则；要先用真实 HTML 定义结果项，再分别写搜索与发现的规则。
