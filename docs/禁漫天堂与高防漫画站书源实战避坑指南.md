## 二、底层机制陷阱 1：`bookUrlPattern` 导致搜索结果全空

### 1. 现象描述
书源可以在发现页（Explore）正常浏览翻页、查看排行榜，但在顶部输入关键词搜索时，转圈结束后直接显示空列表，抓不到任何结果。

### 2. 源码调用链分析（`WebBook.kt` 第 228500~228518 行）
```kotlin
if (isSearch) bookSource.bookUrlPattern?.let {
    currentCoroutineContext().ensureActive()
    if (baseUrl.matches(it.toRegex())) {
        Debug.log(bookSource.bookSourceUrl, "≡链接为详情页")
        getInfoItem(
            bookSource, analyzeRule, analyzeUrl, body, baseUrl,
            ruleData.getVariable(), isRedirect, filter
        )?.let { searchBook ->
            searchBook.infoHtml = body
            bookList.add(searchBook)
        }
        return bookList // 提前返回，不再执行后续搜索列表解析！
    }
}
// 正常的搜索列表解析逻辑在下方，如果上方被提前拦截，此处永远不会被执行：
val collections = analyzeRule.getElements(ruleList)
```

### 3. 产生原因
* 先前为了“全面覆盖域名格式”，将 `bookUrlPattern` 写成了：
  ```regex
  https?:\/\/(?:www\.)?(?:18comic|jmcomic).*\/(?:album|photo|search|albums)[/?].*
  ```
* 搜索发起时，实际请求地址为 `https://18comic.vip/search/photos?search_query=...`。
* 阅读底层判定：`baseUrl.matches(bookUrlPattern.toRegex())` 返回 `true`！
* 阅读误认为用户搜索的是“某本漫画的完整详情页网址”，直接尝试调用详情页解析函数 `getInfoItem()` 从当前页面提取单一标题 `h1#book-name`。
* 搜索结果页是卡片列表，根本没有单本书籍的主标题，提取结果为 `null`，导致列表为空，**而正常的 `ruleSearch.bookList` 被完全短路跳过**！

### 4. 黄金准则
> [!IMPORTANT]
> **`bookUrlPattern` 必须且只能匹配“单一作品详情页”！**
> 绝对不要在 `bookUrlPattern` 中包含 `search`、`albums`、`category` 等列表或搜索路由！
> 
> **正确示范**：
> ```json
> "bookUrlPattern": "https?:\\/\\/(?:www\\.)?(?:18comic|jmcomic|jm-comic)\\w*\\.[a-z0-9]+\\/album\\/\\d+.*"
> ```

## 三、底层机制陷阱 2：`webJs` 轮询超时引发整页白屏

### 1. 现象描述
配置了 `{"webView":true}` 仍然白屏，日志输出 `NoStackTraceException("js执行超时")`。

### 2. 源码调用链分析（`BackstageWebView.kt` 第 194360~194380 行）
```kotlin
private fun handleResult(result: String) = Coroutine.async {
    if (result.isNotEmpty() && result != "null") {
        val content = StringEscapeUtils.unescapeJson(result).replace(quoteRegex, "")
        val response = buildStrResponse(content)
        callback?.onResult(response) // 成功返回
        mHandler.post { destroy() }
        return@async
    }
    if (retry > 30) { // 轮询超过30次，抛出严重异常
        callback?.onError(NoStackTraceException("js执行超时"))
        mHandler.post { destroy() }
        return@async
    }
    retry++
    mHandler.postDelayed(this@EvalJsRunnable, nextDelay)
}
```

### 3. 产生原因
* 书源在 URL 附加参数中加入了动态检测脚本：
  ```json
  "webJs": "document.querySelector('.list-col')?document.documentElement.outerHTML:''"
  ```
* 当路由不匹配、页面 DOM 稍有延迟、或者选择器名称有细微出入时，该 JS 会返回 `""`（空字符串）。
* 阅读检测到返回为空，会触发重试轮询（间隔 200ms~1000ms），直到达到 30 次上限抛出 `js执行超时`。
* 上层调度直接判定请求失败，导致整页渲染空白。

### 4. 黄金准则
> [!TIP]
> 绝大多数情况下，使用阅读原生的 `,{"webView":true}` 即可。阅读在后台 WebView 的 `onPageFinished` 事件触发后，默认执行 `document.documentElement.outerHTML`，毫秒级抓取完整 HTML，完全不需自定义轮询 JS，杜绝超时异常。

## 四、底层机制陷阱 3：规则优先级切分导致 `webView` 参数丢失

### 1. 现象描述
搜索页或发现页列表能展示出来，但点击漫画条目进入后，书名、作者、封面全为空白，抓包发现请求被 Cloudflare 返回 403 Forbidden。

### 2. 源码调用链分析（`AnalyzeRule.kt`）
```kotlin
// getStringList / SourceRule 解析流程：
val ruleAnalyzes = RuleAnalyzer(sourceRule.elementsRule)
val ruleStrS = ruleAnalyzes.splitRule("&&", "||", "%%")
```
阅读在拆解规则时，`||`（备选分支运算符）优先于 `##`（正则替换运算符）生效。

### 3. 产生原因
* 规则原写法：`tag.a.0@href||a@href##$##,{"webView":true}`
* 实际被解析为两个备选分支：
  * 分支 1：`tag.a.0@href` （**注意：结尾没有被追加参数！**）
  * 分支 2：`a@href##$##,{"webView":true}`
* 在列表卡片中，分支 1 成功提取出了类似 `/album/268850/` 的纯相对链接。
* 当阅读发起书籍详情请求时，由于该 URL **不包含 `{"webView":true}` 标头**，阅读退化使用底层的 **OkHttp** 客户端发起原生网络请求。
* Cloudflare 检测到缺乏真实浏览器指纹（TLS 指纹、无 Headless 特征），直接返回 **403 Forbidden**，导致详情页一片空白。

### 4. 黄金准则
> [!IMPORTANT]
> 拼接链接选项参数时，若使用选择器语法，请避免把 `||` 与 `##` 混在同一行引发切分歧义。
> 
> **正确示范（标准 Declarative 写法）**：
> ```json
> "bookUrl": "a.0@href##$##,{\"webView\":true}"
> ```
> 或使用 JS 兜底确保无论走哪个分支都带参数：
> ```json
> "bookUrl": "<js>var u=java.getString('a@href'); u ? (u + ',{\"webView\":true}') : ''</js>"
> ```

## 五、底层机制陷阱 4：`tocUrl` 填写破坏阅读内置目录缓存机制

### 1. 现象描述
详情页内容显示正常，但一点击目录列表，界面长时间加载甚至白屏。

### 2. 源码调用链分析（`BookInfo.kt` 第 228406~228410 行 与 `BookChapterList.kt`）
```kotlin
book.tocUrl = analyzeRule.getString(infoRule.tocUrl, isUrl = true)
if (book.tocUrl.isEmpty()) book.tocUrl = baseUrl
if (book.tocUrl == baseUrl) {
    book.tocHtml = body // 极其关键：直接复用详情页已成功拉取的HTML！
}
```
以及获取章节列表时的优化判断：
```kotlin
if (book.bookUrl == book.tocUrl && !book.tocHtml.isNullOrEmpty()) {
    // 零网络开销，直接解析内存中的 tocHtml！
    BookChapterList.analyzeChapterList(...)
}
```

### 3. 产生原因
* 很多书源作者习惯在 `ruleBookInfo.tocUrl` 中显式填入 `"baseUrl,{\"webView\":true}"`。
* 这会导致 `book.tocUrl` 成为带有参数的字符串，而 `baseUrl` 是不带参数的标准 URL，二者字符串比较不相等（`book.tocUrl != baseUrl`）。
* 阅读因此认为“目录在一个全新的独立页面”，在用户点击目录时又在后台强行开启一个新的 WebView 重新加载一次详情页，造成翻倍的网络请求和延迟；若中途出现风控或波动，目录立即变白。

### 4. 黄金准则
> [!TIP]
> 凡是**目录就在作品详情页内**的站点（绝大多数漫画站点如禁漫、拷贝等）：
> `ruleBookInfo.tocUrl` **必须直接留空（`""`）**！
> 留空后阅读底层会自动判定 `book.tocUrl = baseUrl` 并直接注入 `book.tocHtml = body`，实现**零额外网络消耗、毫秒级秒开目录**。

## 六、网络与风控陷阱 5：WAF、弹窗死循环与 AVS 年龄验证突破

### 1. 为什么会发生死循环弹窗验证？
* **旧方案误区**：在书源中加入 `loginCheckJs` 监控页面，使用正则如 `/(?:challenge|cloudflare|turnstile|verify)/i`。
* **致命后果**：禁漫天堂页面加载的 Google Analytics、广告外链脚本、或者包含的某些单词，经常无意命中上述关键字。
* 每当阅读解析页面，`loginCheckJs` 便返回 `true`，阅读立刻调用 `java.startBrowser` 强行弹出内置浏览器让用户验证；而用户点进去看网页明明是正常的，退出后过几秒又弹，形成死循环。

### 2. 网站原生的 18+ 年龄确认遮罩阻断
* 禁漫天堂新会话首次请求时，服务端会检测 Cookie 中是否存在 `AVS=1`。
* 若缺失，页面虽然输出内容，但在上方覆盖 `#adult_modal` 遮罩层阻碍正常用户交互。
* **解决方案**：
  直接在全局 PC 端请求头中硬编码注入 Cookie，并在书源启用 Cookie 自动托管：
  ```json
  "enabledCookieJar": true,
  "header": "{\n  \"User-Agent\": \"Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/128.0.0.0 Safari/537.36\",\n  \"Accept\": \"text/html,application/xhtml+xml,application/xml;q=0.9,image/avif,image/webp,*/*;q=0.8\",\n  \"Cookie\": \"AVS=1; over18=1\",\n  \"Referer\": \"https://18comic.vip/\",\n  \"sec-ch-ua\": \"\\\"Chromium\\\";v=\\\"128\\\", \\\"Not;A=Brand\\\";v=\\\"24\\\", \\\"Google Chrome\\\";v=\\\"128\\\"\",\n  \"sec-ch-ua-mobile\": \"?0\",\n  \"sec-ch-ua-platform\": \"\\\"Windows\\\"\"\n}"
  ```
  服务端一接收到 `AVS=1`，直接判定访客已通过年龄认证，不会输出阻断弹窗。

## 七、路由陷阱 6：API 接口与 PC 网页端真实路由混淆

### 1. 现象
发现页分类点击后无论切换哪个分类，抓出来的都是空数据。

### 2. 根因剖析
禁漫天堂的路由分为两套体系：
* **内部 AJAX 接口**：`/categories/filter?o=mv&t=t`（只接受特定的 XHR 请求，直接网页访问不返回完整 HTML）。
* **浏览器主渲染路由**：
  - 热门排行：`/albums?o=mv&t=t` (日榜), `/albums?o=mv&t=w` (周榜), `/albums?o=mv&t=m` (月榜), `/albums?o=mv&t=a` (总榜)
  - 综合排序：`/albums?o=mr` (最新), `/albums?o=mp` (最多爱心), `/albums?o=tf` (最多收藏), `/albums?o=md` (最多评论)
  - 板块分类：`/albums/doujin` (同人), `/albums/single` (单行本), `/albums/short` (短篇), `/albums/hanman` (韩漫), `/albums/3d` (3D漫画)
  - 搜索路由：`/search/photos?search_query={{encodeURIComponent(key)}}&main_tag=0&page={{page}}`

## 八、内容与排版陷阱 7：图片 Lazyload 属性乱序与相对路径补全

### 1. 乱序问题
常见错误正则：`/<img[^>]+(?:data-original|src)="([^"]+)"/`
如果 HTML 为：`<img class="lazy" src="placeholder.png" data-original="real_pic.jpg">`，正则首先匹配到 `src`，把占位图当作真实图片存入，导致正文全是 loading 图。

### 2. 相对路径问题
部分 CDN 节点返回相对路径：`/media/photos/268850/00001.webp`，OkHttp 无法直接拉取没有协议头的链接。

### 3. 标准化提取脚本（注入在 `ruleContent.content`）
```javascript
result = (function() {
    var str = (result ? result.toString() : (src ? src.toString() : ""));
    var domain = (baseUrl && baseUrl.match(/^https?:\/\/[^\/]+/i)) ? baseUrl.match(/^https?:\/\/[^\/]+/i)[0] : getDomain();

    var urls = [];
    var seen = {};
    // 1. 获取所有 img 标签
    var imgTags = str.match(/<img\b[^>]+>/gi) || [];
    for (var i = 0; i < imgTags.length; i++) {
        var tag = imgTags[i];
        // 严格按优先级匹配：优先真实切片地址
        var mUrl = tag.match(/\b(?:data-original|data-src)="([^"]+)"/i) || tag.match(/\bsrc="([^"]+)"/i);
        if (mUrl && mUrl[1]) {
            var rawU = mUrl[1].trim();
            // 过滤广告、统计图与头像，只保留漫画图片
            if (rawU.indexOf("media/photos") !== -1 || rawU.indexOf("photos/") !== -1) {
                var u = rawU;
                if (u.indexOf("//") === 0) {
                    u = "https:" + u;
                } else if (u.indexOf("http") !== 0) {
                    u = domain + (u.indexOf("/") === 0 ? "" : "/") + u;
                }
                if (!seen[u]) {
                    seen[u] = true;
                    urls.push('<img src="' + u + '">');
                }
            }
        }
    }
    return urls.join('\n');
})();
```

## 九、高性能本地解码 8：垂直条带倒序拼装 (`imageDecode`)

禁漫天堂自 220980 号本子起，引入了垂直切片混淆。切片分割条数 `num` 基于 `md5(bookId + imgId)` 尾字符的 ASCII 码动态计算。

在 Android 端，阅读支持使用 JavaBridge 直接调用系统底层的 `android.graphics.BitmapFactory` 和 `Canvas`，实现毫秒级硬件级解码，**无需依赖任何外部解码服务器**：

```javascript
(function(result, src) {
    if (!result || result.length === 0) return result;
    if (src.indexOf("gif") !== -1 || src.indexOf("qyyuapi.com") !== -1) return result;

    var mac = src.match(/photos\/(\d+)\/(\d+)/);
    if (!mac || !mac[1] || !mac[2]) return result;

    var bookId = Number(mac[1]);
    var imgId = mac[2];
    if (isNaN(bookId) || bookId < 220980) return result; // 早期作品未混淆

    // 动态计算切片条数
    var num = 10;
    if (bookId > 421925) {
        var md5 = java.md5Encode(bookId + "" + imgId);
        var ascii = md5.substr(-1).charCodeAt(0);
        num = (ascii % 8 + 1) * 2;
    } else if (bookId >= 268850) {
        var md5 = java.md5Encode(bookId + "" + imgId);
        var ascii = md5.substr(-1).charCodeAt(0);
        num = (ascii % 10 + 1) * 2;
    }

    var Magua = new JavaImporter();
    Magua.importPackage(Packages.java.io, Packages.android.graphics);
    with (Magua) {
        try {
            var img = BitmapFactory.decodeByteArray(result, 0, result.length);
            if (!img) return result;
            var height = img.getHeight();
            var width = img.getWidth();
            var y = Math.floor(height / num);
            var remainder = height % num;
            var newImg = Bitmap.createBitmap(width, height, Bitmap.Config.ARGB_8888);
            var canvas = new Canvas(newImg);
            // 倒序重组切片
            for (var i = 1; i <= num; i++) {
                var h = (i === num) ? remainder : 0;
                var srcBlock = Bitmap.createBitmap(img, 0, y * (i - 1), width, y + h);
                canvas.drawBitmap(srcBlock, 0, height - y * i - h, null);
            }
            var newbit = new ByteArrayOutputStream();
            newImg.compress(Bitmap.CompressFormat.JPEG, 92, newbit);
            return newbit.toByteArray();
        } catch (e) {
            return result;
        }
    }
})(result, src);
```

## 十一、API 体系书源实战对比：移动端原生接口（JMComic App API）避坑分析

除了前述网页端（HTML + WebView）架构外，部分高阶书源会直接对接官方移动端 API（如禁漫天堂 JMComic App）。虽然 API 源速度极快（省去了渲染 HTML、加载广告的开销），但其**签名鉴权与加解密机制**也带来了完全不同的踩坑点。

### 1. 网页版 vs API 版的本质差异对比

| 维度 | 网页版书源（`18comic.vip` 等） | 原生 API 版书源（`禁漫天堂api.json`） |
| :--- | :--- | :--- |
| **通信协议** | 标准 HTTP 访问 HTML 网页 | HTTP RESTful JSON 接口（`/search`, `/album`, `/chapter`） |
| **反爬防御** | Cloudflare 5 秒盾、Turnstile 交互验证、JS 逆向防抓取 | 动态时间戳鉴权（`tokenparam`）、AES/ECB/PKCS7 加密载荷 |
| **请求载体** | 阅读内置浏览器（WebView）全功能渲染 | 阅读 Java 原生网络请求（OkHttp），零渲染开销 |
| **数据解析** | CSS / XPath / Jsoup 提取 DOM 节点 | AES 解密密文为 JSON，直接 `JSON.parse` 提取字段 |
| **搜索排查难点** | 网页重定向、验证弹窗、元素选择器失效 | **Token 签名缺失返回 401、UA 缺失被 WAF 拦截 403、变量初始化时序漏洞** |

---

### 2. API 版书源搜索为空的 6 大根因定位

在排查 `禁漫天堂api.json` 搜索为空时，我们发现了以下典型问题链：

#### 根因 1：`header` 缺失动态鉴权头 `tokenparam`，初始请求被拒（401）
* **现象**：JMComic API 的搜索接口 `/search?search_query=xxx&page=1` 对请求合法性有严格校验。
* **机制**：服务端强制要求请求头包含 `tokenparam: {timestamp},{version}`。若缺失，直接返回 `{"code":401,"data":[],"errorMsg":"Not legal request."}`。
* **漏洞**：原书源在全局 `header` 中只有 `User-Agent` 与 `Cookie`，没有注入 `tokenparam`。阅读发起的第一次搜索请求直接 401 失败。

#### 根因 2：未初始化状态导致 `undefined` 缓存穿透与 URL 畸形
* **时序陷阱**：在阅读中，初次导入书源或搜索时，`source.header` 会先于 `searchUrl` 执行。
* **致命链条**：此时 `source.getVariable()` 仍为空，`Get('url')` 返回 `undefined`。
  1. `header` 将请求头存入了 `cache.put(md5("undefinedheaders"), ...)`；
  2. 后续规则调用 `Getdata` 时以真实域名 `cache.get(md5("https://www.cdnhjk.netheaders"))` 取值，永远取到 `null`；
  3. `Getdata` 甚至执行了 `java.ajax(Get('url') + '/setting')`，直接请求了畸形链接 `"undefined/setting"`，抛出 `MalformedURLException: no protocol: undefined/setting`。

#### 根因 3：JavaScript 短路逻辑漏洞导致请求头裸奔（403 Forbidden）
* 原书源中有这样一段容错代码：
  ```javascript
  headers = JSON.parse(cache.get(...) || '{}') || { 'User-Agent': '...' };
  ```
* **严重逻辑缺陷**：在 JavaScript 中，`{}`（空对象）是 **Truthy（真值）**，`Boolean({}) === true`！
* 当 cache 为空时，`JSON.parse('{}')` 返回 `{}`，后面的 `|| { 'User-Agent': ... }` **根本不会执行**！
* 结果 `headers` 沦为没有任何 `User-Agent` 的空对象。Cloudflare WAF 遇到没有 UA 的请求，会直接抛出 **HTTP 403 Forbidden**，搜索请求在网关层被瞬间掐断。

#### 根因 4：无效的 `AVS=` 检查与同步阻塞
* API 接口与网页版不同，调用 `/setting` 时只返回基础配置，**不返回也不依赖 `AVS` Cookie**。
* 原代码每次请求都检查 `!/AVS=/.test(headers.Cookie)`，导致每次调用都同步发起一次多余的 `/setting` 请求，既白白浪费 1~2 秒，又增加了请求失败率。

#### 根因 5：搜索关键词未转义与空格暴力腰斩
* 原书源 `searchUrl` 中的清洗逻辑：
  ```javascript
  search_query=${e.replace(/\s.*$|\/.*$/g, '')}
  ```
* **缺陷 1**：没有使用 `encodeURIComponent`，中文或特殊字符传给 API 可能会丢失编码。
* **缺陷 2**：`\s.*$` 会将关键词中第一个空格后面的所有内容**暴力截断**。用户若搜索带空格的漫画（如 `秘密 教学`），实际被截断成 `秘密`，复合搜索完全失效。

#### 根因 6：双重网络请求的性能损耗
* 阅读发起搜索时，本身已经通过 `searchUrl` 执行了一次网络请求并把响应存入 `result`。
* 原书源在 `ruleSearch.bookList` 中完全舍弃 `result`，又重新调用 `Getdata(baseUrl)` 再次发起 HTTP 请求，导致搜索速度慢一倍。
