# 起点图网书源错误分析与避坑修复指南

## 一、 背景与定位

[起点图网.json](file:///d:/Codes/项目/AiWritingLegado/book_sources/起点图网.json) 对应的数据站点为 **起点图**（`https://www.qidiantu.com/`）。
该站点的定位是 **起点中文网的数据分析与书单书评平台**（提供昨日新书首订榜、月度首订、盟主榜、潜力榜、大神新书、荣誉徽章、起点封推/强推/三江推荐、书单评论等），**不是**提供小说正文章节的阅读站点。
在阅读 App 中，该书源的核心价值在于**发现好书、查阅网文行业数据与书友书评**。

---

## 二、 核心错误原因深度复盘

本次排查共诊断出 **5 大典型技术错误**，覆盖了网络反爬、分页越界、接口变动、选择器规范以及底层 JavaScript 引擎（Rhino）跨语言调用的致命陷阱。

---

### 错误 1：直连高防第三方站点导致的大面积白屏（WAF 反爬拦截）

#### 1. 现象描述
在书源发现分类中，原本配置了 40 余个“起点榜单”（包括月票榜、推荐榜、收藏榜、玄幻/都市/仙侠等分类排行、完本榜、畅销榜等），用户在阅读 App 中点击任何一个榜单进去都是**一片空白、没有任何书籍**。

#### 2. 根本原因
* 原书源在这些分类中直接配置了起点中文网官网的 URL：`https://www.qidian.com/rank/yuepiao/page{{page}}` 等。
* 起点中文网官方目前开启了**高强度腾讯云 WAF 反爬保护机制**。当使用手机客户端的简单 HTTP 请求（缺少浏览器指纹和会话 Cookie）访问时，服务器直接返回 **HTTP 202 状态码**，响应内容仅有 209 字节的 `<script src="/probe.js">` 质询探针。
* 阅读 App 无法执行探针过盾，解析到的 HTML 只有空 body，因此提取到的图书列表为 0，页面全白。

#### 3. 避坑原则
> [!WARNING]
> * **切忌在书源中随意嫁接外部未逆向破防的高防站点**。本站数据源是哪个网站，发现分类就应严格使用该网站本站的原生路由。
> * 若外部源开启了 JS Challenge、WAF 盾或 Cloudflare 质询，简易 HTTP 请求必死，必须剔除或使用专门的过盾代理/WebView 处理。

### 错误 2：随机数生成算法未校准站点分页引发的 HTTP 567 崩溃

#### 1. 现象描述
在发现列表中点击“书单2”或“书单3”，有大概率或必然出现**点进去没内容**，甚至控制台报错。

#### 2. 根本原因
* 原书源在 `exploreUrl` 中为书单配置了随机获取页面的 JS 逻辑：
  * 书单2：`i1 = Math.floor(Math.random() * 17) + 4;` （随机生成 4 ~ 20 页）
  * 书单3：`i1 = Math.floor(Math.random() * 40) + 21;` （随机生成 21 ~ 60 页）
* 经实测抓包，起点图网站的书单索引页 `/booklists/` **目前只有 0 ~ 4 页（共 5 页）**！
* 当请求第 5 页及以后的地址时（如 `/booklists/5/`、`/booklists/20/`），服务器直接响应 **HTTP 567 异常状态码**；导致 `.match(/booklist\/\d+/g)` 返回 `null`，后续执行 `null[0]` 抛出 `TypeError` 异常，URL 拼接成 `undefined/0` 导致 404。

#### 3. 避坑原则
> [!IMPORTANT]
> * 书源编写动态规则（尤其是随机数、页码偏移、日期回退）时，**必须先行探查目标站点的实际数据量与有效分页范围**。
> * 动态计算必须编写**完备的空值容错和兜底保障**，例如 `(m ? (m[idx] || m[0]) : 'booklist/defaultId')`，防止上游改动导致客户端抛错闪退。

### 错误 3：搜索接口变动 404 与 JSoup 类选择器带空格语法失效

#### 1. 现象描述
在搜索框中搜索任何小说（如“宿命之环”、“全职高手”），结果直接显示**搜索失败：HTTP状态码 404**，没有任何结果，自然也不会显示书籍图片。

#### 2. 根本原因
* **接口变更（404）**：原书源使用的搜索链接为 `https://www.qidiantu.com/book/`，此接口在原网站改版后已被彻底废弃并返回 404。通过分析网站前端 `search.php` 内绑定的 `booknamesearch()` 函数，实际有效接口已变更为：
  ```javascript
  window.location.href = "/bookxyy/" + value;
  ```
* **JSoup 类名解析缺陷**：原 `ruleSearch.coverUrl` 编写为：
  ```json
  "coverUrl": "class.media-left media-middle@a@img@src"
  ```
  在阅读底层的 JSoup 解析中，`class.` 后面的规则会被传入 `Element.getElementsByClass(className)`。在 JSoup 规范中，**类名参数严禁带有空格**（空格被视为复合类），传入带有空格的类名会导致定位失败或返回空集合。

#### 3. 避坑原则
> [!TIP]
> * 遇到搜索 404 或无响应，优先检查网页源代码中的 `<form action="...">` 或绑定的 `onkeydown`/`onclick` JavaScript 提交逻辑。
> * 在阅读原生规则中，尽量避免写 `class.类名A 类名B`；若需要层级定位，在单个卡片内通常直接用标签即可（如 `img@src`），或者使用标准的 CSS 选择器 `@css:.media-left img@src`。

### 错误 4：封面规则硬编码列索引与结构遗漏导致图片大面积缺失

#### 1. 现象描述
* 发现里的“起点推荐”（封推、强推、三江等）所有书籍**完全没有封面**；
* 发现里的“书单”点进去后，里面列出的书籍**也全都没有封面**；
* 部分榜单在网站改版列顺序微调后，封面解析直接落空。

#### 2. 根本原因
* **推荐榜完全遗漏**：在原 `ruleExplore.coverUrl` 的庞大 `if-else` 分支中，包含了 `booklist/`、`shouding/`、`badge/`、`twelvekings` 等，但**唯独完全漏掉了 `bang/`**！匹配不到任何条件时直接返回 `undefined`，推荐榜书籍全部失去封面。
* **书单提取逻辑目标元素错误**：书单详情页中，书籍卡片是 `.well.well-sm.table-responsive`，而原规则写了：
  ```javascript
  s = java.getString('class.panel-heading.0@a.0@href');
  ```
  `.panel-heading` 是书单顶部的标题框才有的类，每本书的容器里根本没有这个元素，提取出来的 `s` 为 `""`，随后执行 `s.match(/\d+/)[0]` 直接崩掉。
* **硬编码 `td` 列位极度脆弱**：首订榜作者在 `td.7`、月度首订在 `td.3`、盟主榜在 `td.3`、十二天王在 `td.5`，原规则针对不同 URL 写了大量 `x('td.1@a.0@href')`、`x('td.2@a@href')`，极易因前端排版改动而全部失效。

#### 3. 避坑原则
* **寻找全站业务核心统一主键**：
  在起点图网站中，不论是表格 `tr`、书单卡片 `well` 还是搜索卡片 `media`，书籍链接的地址恒定为：
  $$\text{URL 模式: } \texttt{/info/\{bookId\}}$$
  而起点官方的高清封面 CDN 结构恒定为：
  $$\text{封面 CDN: } \texttt{https://qidian.qpic.cn/qdbimg/349573/\{bookId\}/180}$$
  直接抓住这个核心本质，不论书在第几个 `td`，统一从包含了 `/info/` 的链接中提取纯数字书号即可，一行逻辑覆盖全站，永远不会因列顺序调整而失效。

### 错误 5：Mozilla Rhino 引擎对 Java 对象的重载匹配冲突（EvaluatorException）

#### 1. 现象描述
用户在阅读 App 中点击进入「新书潜力榜」时，弹出红色错误提示：
```text
com.script.ScriptException: org.mozilla.javascript.EvaluatorException: 
对应于 JavaScript 参数类型 (object,string) 的 Java 方法 java.lang.String.replace 的选择不明确。
建议的方法是：
  class java.lang.String replace(java.lang.CharSequence,java.lang.CharSequence)
  class java.lang.String replace(char,char) (<Unknown Source>#7) in <Unknown Source> at line number 7
```

#### 2. 根本原因
* 阅读 App 在 Android 端运行 JavaScript 规则时使用的是 **Mozilla Rhino 引擎**。
* 在规则的 `<js>` 环境中，调用 `java.getString(...)` 返回的是**原生 Java 的 `java.lang.String` 实例**，而不是 JavaScript 内置的 `String` 原型。
* 在 Java 语言中，`java.lang.String.replace` 只有两个重载方法：
  * `replace(CharSequence target, CharSequence replacement)`
  * `replace(char oldChar, char newChar)`
* 原规则写成了：
  ```javascript
  java.getString('h4@text||a@text||text').replace(/（点击查看推荐效果）/g, '').trim();
  ```
* 传入的第一个参数是 JavaScript 的 `RegExp` 对象（类型为 `object`），第二个参数是 `string`。Rhino 试图在 Java 的 `java.lang.String` 类上寻找匹配的方法，但发现既不是两个字符，也不是两个字符串序列，因此抛出“方法选择不明确”的致命异常，导致列表加载中断。

#### 3. 避坑原则
> [!CAUTION]
> 1. **优先使用阅读原生规则（免 JS 脚本）**：
>    能用原生 CSS + 正则替换的，**坚决不写 `<js>`**！原生规则由 Kotlin + JSoup 在底层直接执行，执行速度比 Rhino 快数十倍，且 100% 不会发生 Rhino 跨语言类型转换崩溃。
>    例如：
>    ```json
>    "name": "@css:a[href*=\"/info/\"]@text||h4@text##^\\[.*?\\]",
>    "author": "@css:a[href*=\"/author/\"]@text##\\(Lv\\.\\d+\\)|^Lv\\.\\d+",
>    "bookUrl": "@css:a[href*=\"/info/\"]@href##/[dm]$"
>    ```
> 2. **若必须在 JS 中对 Java 字符串做正则操作，必须先显式包装为 JS 原生 String**：
>    ```javascript
>    // ❌ 危险写法：对 Java 字符串直接调 JS 正则
>    java.getString('xxx').replace(/abc/g, '');
>
>    // ✔️ 安全写法：强制转为 JS 原生字符串后再调
>    String(java.getString('xxx') || '').replace(/abc/g, '');
>    ```

## 四、 书源编写自查防错 Checklist

今后在编写或优化其他书源时，请务必参照以下清单逐一核对：

* [ ] **接口可用性**：新旧接口是否已通过控制台或抓包验证？是否存在 404/302 重定向？
* [ ] **WAF 风险排查**：是否混入了外部高防站点（如起点、纵横、晋江官网等带有验证探针的链接）？
* [ ] **分页边界防守**：动态生成的分页数值是否超出目标站点实际存在的最大页数？
* [ ] **选择器规约**：
  * 是否使用了形如 `class.foo bar` 带空格的选择器？（严禁空格，改用单类名或 `@css:.foo.bar`）
  * 是否优先使用阅读原生语法（`@css:`、`##match##replace`），而非盲目滥用 `<js>`？
* [ ] **Rhino 跨语言安全**：
  * JS 中调用 `java.getString(...)` / `java.ajax(...)` 的结果是否立即使用 `String(...)` 包装？
  * 是否存在对 Java 对象直接传入 RegExp 调用 `.replace()` 的代码？
* [ ] **容错保底**：列表为空、正则没匹配到时，是否有空值安全判断？（使用可选链或 `|| ''` 兜底）
* [ ] **真机与环境一致性**：编写完成后，不仅在 Python 调试引擎下运行，还需在真实 Android/iOS 阅读客户端的 Rhino 环境中导入并跑通发现与搜索全流程。
