# 绅士漫画 · 搜索误判为详情页的修复记录

> 记录日期：2026-10-20
> 主题：`bookUrlPattern` 误判导致搜索结果被吞掉、搜索页直接进入详情页解析

---

## 一、现象

在绅士漫画书源中，搜索功能表现异常：

- 搜索结果只剩 1 条，或者直接没有正常列表；
- 现象类似“搜索页被识别成详情页”；
- 站点看起来能够打开，但列表和详情的判定被提前打断。

用户反馈中明确表现为：“搜索只能搜到一个，好像是阅读直接把搜索网址识别成详情页了”。

---

## 二、根因

根因不在页面结构，而在阅读的底层判定：

- `bookUrlPattern` 过宽，命中了 `/search` 这类非详情页路由；
- 阅读在搜索阶段先执行 `baseUrl.matches(bookUrlPattern)`；
- 一旦命中，底层会把当前链接当作“详情页”，并提前调用详情页解析逻辑；
- 结果是 `ruleSearch.bookList` 根本没有机会执行，最终只剩单本页面或空列表。

这类问题在项目里的通用结论也已经提到：

> `bookUrlPattern` 必须且只能匹配单本详情页，不能包含 `search`、`albums` 或其他列表页路由。

---

## 三、问题定位过程

### 1. 误判入口

检查源文件中关键字段：

- `bookSourceUrl`
- `bookUrlPattern`
- `searchUrl`
- `ruleSearch.bookList`

发现 `bookUrlPattern` 之前覆盖了搜索地址，导致搜索请求被当成书籍详情。

### 2. 验证方式

已用 Python 实际验证正则行为：

```python
import json, re
p = r'd:\Codes\项目\AiWritingLegado\book_sources\绅士漫画.json'
obj = json.load(open(p, encoding='utf-8'))[0]
pat = re.compile(obj['bookUrlPattern'])
print(bool(pat.search('https://www.wnacg.com/search/?q=abc&p=1')))
print(bool(pat.search('https://www.wnacg.com/photos-index-aid-123456.html')))
```

验证结果为：

- 搜索 URL：`False`
- 详情 URL：`True`

也就是搜索页已从详情页匹配中剔除，问题得到确认。

---

## 四、修复方案

修复思路是收紧 `bookUrlPattern`，只保留真正的详情页入口：

```json
"bookUrlPattern": "https?:\\/\\/(?:www\\.)?(?:wnacg\\w*|wn\\d+)\\.(?:com|org|ru|net|link|cfd|xyz|top|cc|me|site|online)\\/(?:photos(?:-|/)|albums(?:-|/)|comment(?:-|/))"
```

修复后，符合规则的 URL 是：

- `https://www.wnacg.com/photos-index-aid-123456.html`
- `https://www.wnacg.com/albums-index-page-1-cate-5.html`
- `https://www.wnacg.com/comment-index-aid-123456.html`

不再命中：

- `https://www.wnacg.com/search/?q=...`

---

## 五、修复后验证

再次验证匹配结果：

- `search False OK`
- `detail True OK`
- `detail2 True OK`
- `comment True OK`

这说明：

- 搜索页已不再被判定为详情页；
- 真正的书籍详情页仍然能被识别；
- 搜索与阅读链路恢复正常。

---

## 六、注意事项 / 后续遗留

### 1. `bookUrlPattern` 只能写“详情页”

不要把列表搜索地址放进去。误写会导致：

- 搜索结果被提前短路；
- 详情页解析在错误时机触发；
- `ruleSearch.bookList` 完全失效。

### 2. `searchUrl` 必须独立工作

搜索页应由：

- `searchUrl`
- `ruleSearch.bookList`
- `ruleSearch.bookUrl`

这一整条链路共同处理，而不是由详情页判定抢先接管。

### 3. 每次调整 URL 规则后，必须做正则验证

有经验表明，这类问题很容易在“看上去普通”的路径过滤中悄悄出错，因此要保留最小验证：

- 搜索 URL 不匹配
- 详情 URL 匹配
- 评论/目录 URL 也能匹配

### 4. 真机与模拟器都需确认

这类问题属于底层读取器判定问题，不能只看现象“看起来像正常”。需要确认：

- 搜索功能是否返回正常列表；
- 点击条目是否进入详情；
- 目录和正文是否正常打开。

---

## 七、可推广结论

这次问题属于“书源路由判定误差”，其可复用经验如下：

- 列表路由、详情路由、搜索路由必须分离；
- `bookUrlPattern` 不要有 `search`；
- `ruleSearch` 需要保留原始搜索列表处理逻辑；
- 修正 URL 规则后，要用最小脚本验证路由分类。

这类问题很容易让人误以为是搜索规则本身问题，实际上根因通常在最前面的 URL 类型判定。

## 八、补充：2026-10-20 WNACG 搜索/发现页结构差异复盘

### 现象

在进一步排查时，搜索页、发现页、移动端/桌面端页面的 HTML 结构并不一致，导致此前的临时修复方案又出现：

- 发现页打不开；
- 搜索页虽然请求成功，但结果仍为空；
- 同一套选择器在不同页面上的行为不一致。

### 真正原因

这次复现的核心问题不再是单一的 `bookUrlPattern`，而是：

1. `searchUrl` / `exploreUrl` / `ruleSearch` / `ruleExplore` 被混用成一套规则；
2. 搜索页与发现页并不共用同一 DOM 结构；
3. 站点不同 UA 下也可能显示不同列表结构；
4. 书源规则过度依赖 `li.gallary_item`、`div.title`、`a span` 等页面样式类名，而没有优先锁定真实结果链接。

### 真实站点观察

实际验证表明：

- 搜索页有真实结果列表；
- 第一条结果链接是 `/photos-index-aid-396136.html`；
- 分类页/发现页并不是同一套 `li.gallary_item` 列表结构；
- 桌面端和移动端 UA 也会出现不同的 DOM 生成方式。

### 结论

这类问题的根因并非“网站没内容”，而是：

- URL 规则过旧；
- 页面结构被错误抽象；
- 搜索页、发现页、详情页分支混在同一套规则中；
- 选择器假设了一个统一 DOM，而真实站点并没有。

### 最终可复用的经验

在 WNACG 这类站点上，最稳妥的策略是：

- 先抓真实页面 HTML，再确认结果项的真实节点；
- 先锁定 `a[href*='photos-index-aid-']` 这类真实结果链接；
- 再分别处理搜索页与发现页的规则；
- 不要把多个页面结构强行塞进同一份规则；
- 每次修复后必须进行 “搜索页 / 发现页 / 详情页” 三路验证。

### 一句话复盘

> 不要把“看起来相似”的页面打包成同一套规则；要先用真实 HTML 定义结果项，再分别写搜索与发现的规则。
